# Segfault and Memory Corruption Investigation: php-firebird Extension

**Date**: 2026-01-03
**Status**: ✅ FIXED in v7.0.0-rc.42 (PHP 8.4+)
**Issue**: https://github.com/satwareAG/php-firebird/issues/56
**Last Updated**: 2026-01-03 (v7.0.0-rc.42 verified to fix PHP 8.4 segfault)

## Summary

Memory corruption errors occur during PHP request shutdown after running the doctrine-firebird-driver test suite. Two distinct error manifestations have been observed:

1. **SIGSEGV (Segmentation Fault)** - Exit code 139
2. **`zend_mm_heap corrupted`** - Exit code 134 (SIGABRT)

Both errors occur during PHP's resource cleanup phase (`zend_shutdown_executor_values`) and are likely caused by the same root issue in the php-firebird extension's memory management.

## Environment

- **PHP Version**: 8.4.16
- **php-firebird Extension**: v7.0.0-rc.42 (fixed), previously v7.0.0-rc.37
- **Firebird Server**: 4.0
- **Test Framework**: PHPUnit 10.5.60
- **Docker**: Containerized test environment

## Resolution Summary

| Version | PHP 8.4 | PHP 8.1 |
|---------|---------|---------|
| v7.0.0-rc.37 | ❌ Exit 139 (SIGSEGV) | ❌ Exit 139 |
| **v7.0.0-rc.42** | ✅ **Exit 0** | ❌ Exit 139 |

**v7.0.0-rc.42 fixes the segfault on PHP 8.4.** PHP 8.1 may require additional fixes or is approaching EOL support.

## Investigation Results

### 1. Critical Finding: USE_ZEND_ALLOC=0 Eliminates Crash

```bash
USE_ZEND_ALLOC=0 php vendor/bin/phpunit -c tests/phpunit-firebird4.xml --no-coverage
# Result: Exit code 0 - NO CRASH
```

**Interpretation**: When the Zend Memory Manager is bypassed (using system malloc instead), the crash does not occur. This strongly indicates:

1. The php-firebird extension is incorrectly interacting with Zend MM
2. Possible causes:
   - Memory freed that was not allocated by Zend MM
   - Double-free of Zend-allocated memory
   - Use-after-free of Zend-allocated structures
   - Buffer overflow corrupting Zend MM heap metadata

### 2. GDB Analysis

```bash
gdb -batch -ex 'handle SIGSEGV stop' -ex 'handle SIGABRT stop' \
  -ex 'run -d pcov.enabled=0 vendor/bin/phpunit -c tests/phpunit-firebird4.xml --no-coverage' \
```

**Output:**

**Interpretation:**
- `si_code=SI_KERNEL` - Signal generated by kernel (invalid memory access)

Demangled: `fb::ServiceWrapper::detach(long*)`

The crash occurs in the `ServiceWrapper::detach()` method during resource cleanup.

## Root Cause Hypothesis

Based on the debugging evidence:

### Primary Hypothesis: Memory Allocator Mismatch

The php-firebird extension appears to be freeing memory using a different allocator than what allocated it:

1. **Evidence**: `USE_ZEND_ALLOC=0` eliminates the crash
2. **Mechanism**: When PHP uses its internal Zend MM, the extension may call:
   - `free()` on memory allocated with `emalloc()`
   - `efree()` on memory allocated with `malloc()`
   - Or double-freeing memory

### Secondary Hypothesis: Use-After-Free in Resource Destructor

The `ServiceWrapper::detach()` destructor may be accessing an object that has already been destroyed:

1. **Evidence**: RDI contains ASCII data ("Builder") instead of valid pointer
2. **Evidence**: Crash occurs during `zend_shutdown_executor_values`
3. **Mechanism**: Resource cleanup order may destroy dependencies before dependents

### Tertiary Hypothesis: Double-Free of Service Handle

1. **Evidence**: RBX register previously showed `0x6946656e69727463` (ASCII "ctriFind" - corrupted)
2. **Mechanism**: The same service handle may be detached/freed multiple times

## Recommendations for php-firebird Developers

### Areas to Investigate in C Code

1. **`ServiceWrapper::detach()` method**
   - Check if the service handle is valid before detaching
   - Verify the handle hasn't already been released
   - Add NULL checks and state validation

2. **Memory allocation patterns**
   - Audit all `malloc()`/`free()` vs `emalloc()`/`efree()` usage
   - Ensure consistency: Zend resources use Zend allocator, internal data uses system allocator
   - Check for mixed allocator usage

3. **Resource destructor registration**
   - Review `php_fbird_le_*` resource destructors
   - Ensure proper cleanup order for dependent resources
   - Consider using reference counting to prevent use-after-free

4. **PHP 8.4 compatibility**
   - Review any changes to resource handling in PHP 8.4
   - Check if `zend_shutdown_executor_values` behavior changed

### Suggested Debug Build Steps

```bash
# Build php-firebird with debug symbols and address sanitizer
./configure CFLAGS="-g -O0 -fsanitize=address" LDFLAGS="-fsanitize=address"
make clean && make

# Run tests
ASAN_OPTIONS=abort_on_error=1:halt_on_error=1 php test.php
```

### Code Pattern to Check

```c
// Potential problematic pattern:
static void php_fbird_service_dtor(zend_resource *rsrc) {
    fb_service_t *service = (fb_service_t *)rsrc->ptr;
    
    // BUG: service->wrapper may already be freed
    if (service->wrapper) {
        service->wrapper->detach(&status);  // CRASH HERE
    }
    
    efree(service);  // or free()? Allocator mismatch?
}

// Suggested fix pattern:
static void php_fbird_service_dtor(zend_resource *rsrc) {
    fb_service_t *service = (fb_service_t *)rsrc->ptr;
    
    if (service == NULL) return;  // NULL check
    
    if (service->wrapper && service->wrapper_valid) {
        service->wrapper->detach(&status);
        service->wrapper_valid = false;  // Mark as detached
    }
    
    efree(service);  // Consistent allocator
}
```

## Workarounds

### 1. CI Pipeline Exit Code Handling

Scripts `docker-cqc.sh` and `cqc.sh` use `${PIPESTATUS[0]}` with tee to detect test success before the crash:

```bash
vendor/bin/phpunit ... 2>&1 | tee output.log
phpunit_exit=${PIPESTATUS[0]}
if [[ $phpunit_exit -eq 0 ]]; then
    echo "Tests passed (ignoring post-test crash)"
fi
```

### 2. Bypass Zend MM (Development Only)

```bash
USE_ZEND_ALLOC=0 php vendor/bin/phpunit ...
```

**Warning**: This is NOT recommended for production as it bypasses PHP's optimized memory management.
